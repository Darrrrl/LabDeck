# 006 — Limited web-started SMART self-tests

Status: accepted for the owner's 2026-10-01 request; host validation pending.

The owner requested a way to start short and extended drive tests from the web interface, superseding decision 004's no in-app start rule for this operation only. The optional root-owned `labdeck-smart-control` service listens on a group-restricted Unix socket in the existing SMART snapshot directory. The app container receives the control group and connects through its existing read-only host directory mount. It still has no raw device, root, Docker socket, or general command access.

The browser sends only a configured disk ID and `short` or `extended`. The server requires an owner session, exact origin and CSRF token, and fresh readable ATA evidence. The host service resolves the ID against root-owned configuration, revalidates the reviewed `/dev/disk/by-id/` block path, invokes only `/usr/sbin/smartctl -t short|long -d TYPE PATH` with a ten-second deadline, discards raw output, and limits repeat requests per disk for one minute. A successful exit is reported as **started**, never as passed. Normal snapshot collection later supplies progress and results. No SQLite migration is needed because requests and results are not stored as a new capability.

This is an opt-in control boundary. Socket group membership grants the ability to request tests for every configured disk, so only the app container should receive it. The root-owned socket directory must not be writable by that group. The service is deliberately separate from the periodic read helper and cannot run arbitrary commands or accept paths. The short in-memory rate limit resets on service restart; smartctl and drive firmware may reject a request while a test is running. Operational logs should record only safe disk IDs, type and outcome, not raw device paths or smartctl output. Host compatibility and physical test execution remain unverified until the Ubuntu live gate.
