# Decision 008: one-share host file service

The requested file feature includes writes. The app container continues to receive only sanitized snapshots and a group-restricted Unix socket in the existing read-only collector-public mount. A separate unprivileged Python 3 host service owns the selected mount access and accepts fixed list, upload start/chunk/finish, rename, empty-directory/file delete, and mkdir operations. The root-owned collector configuration selects one of up to four observed SMB/NFS shares. The service resolves paths with directory file descriptors and `O_NOFOLLOW`, rejects traversal/special entries and nested mounts by Linux mount ID, checks the exact remote mount before every operation, and uses no-replace rename/link semantics to reject collisions. It does not offer arbitrary commands, file download, recursive deletion, or cross-share moves.

Uploads use sequential 4 MiB chunks, an opaque 128-bit session ID, durable offset metadata and a temporary file in `.labdeck-uploads` on the selected share. The 100 GiB cap is enforced in both app and host service. Completion links the temporary regular file into the requested destination only when no entry already exists. A browser refresh can resume by selecting the same file; abandoned temporary files require operator cleanup. File contents and paths are not stored in SQLite action audit records. SQLite backup/restore does not include the share.

An owner session, exact origin and CSRF are required for all file operations, including directory listing. The app checks fresh cached share state before connecting to the service; the host independently checks mount identity. The ordinary collector probes each share in an isolated subprocess with a deadline and retains prior capacity with its original evidence time. This is an explicit user-requested scope extension beyond the original observation-only V1 boundary. Real NFS/SMB and systemd permission behavior require Ubuntu validation.
